# Задание 8.I — конструктор перемещения и оператор присваивания с перемещением

Класс `QuadrupedRobot` (см. `docs/shared.pdf`, задания от 09.10) дополнен
перемещающими методами и демонстрацией их отличий от копирующих.

## п.1. Что добавлено в класс

```cpp
QuadrupedRobot(QuadrupedRobot&& o) noexcept;
QuadrupedRobot& operator=(QuadrupedRobot&& o) noexcept;
```

Класс владеет динамическим массивом `last10` (10 значений), поэтому разница
между копированием и перемещением **наблюдаема**, а не «на слово»:
копирование выделяет свой буфер и переписывает 10 значений, перемещение
забирает буфер у источника.

Ключевые решения:

| Место | Решение | Зачем |
|---|---|---|
| `noexcept` на обоих методах | обязательно | Без него `std::vector` при релокации буфера обязан давать strong guarantee и **копирует** элементы вместо перемещения. Проверено тестом `MovingMethodsAreNoexcept` и шагом 6 демо |
| `o.last10 = nullptr` | после кражи буфера | Иначе деструктор источника освободил бы тот же массив второй раз (double free) |
| Перемещённый объект | «пустой»: `last10 == nullptr`, имя/команда пустые | Состояние, в котором объект можно только уничтожить или присвоить; `isMovedFrom()` это открыто сообщает |
| `releaseBuffer()` / `ensureBuffer()` | буфер создаётся лениво | Перемещённому объекту можно вернуть данные через `setLast10()` / `operator>>`, и он снова рабочий |
| `uid`, `id` убраны из `const` | стали обычными полями | `const`-поле запрещает оператор присваивания по умолчанию — в Task7 приходилось вымучивать `const_cast`. Запрет изменить `id` теперь обеспечен отсутствием сеттера |
| Проверка `checkId()` до аллокации | массив выделяется после проверки | При исключении из тела конструктора деструктор **не** вызывается — иначе утечка. Поймано тестом `EmptyIdThrowsAndLeaksNothing` |
| `if (this != &o)` в move-присваивании | защита от `x = std::move(x)` | Иначе освободили бы собственный буфер и взяли данные из него же |

Для измерения в классе появились счётчики: вызовы copy/move ctor, copy/move
assign, число `new double[]` / `delete[]` и число буферов «в воздухе»
(`getLiveBuffers()`).

## п.2. Демонстрация (`main.cpp`)

Запуск: `build/robot.exe`. Каждый шаг печатает адрес буфера и счётчики:

1. **copy ctor** — буфер у копии ДРУГОЙ (`addr` отличается), `+1` аллокация,
   источник не изменился.
2. **move ctor** — буфер тот же по адресу (`0x…58 -> 0x…58`), `0` аллокаций,
   источник стал `moved-from`; затем ему вернули данные — объект снова рабочий.
3. **copy assign** — буфер получателя переиспользован (`0` аллокаций), значения
   скопированы, источник цел.
4. **move assign** — свой буфер освобождён (`delete[] = 1`), чужой украден
   (`0` аллокаций), источник стал `moved-from`.
5. **Без `std::move` перегрузка НЕ выбирается**: `Robot b(a)` и `b = a` дают
   копирование, перемещение — только у x-value.
6. **Куда это идёт само**: `return` из функции (NRVO) и `push_back(makeRobot())`
   в цикле — 8 вставок в `vector` дают `copy ctor = 0`, `move ctor = 15`;
   `v[0]` (l-value) — снова копирование.
7. Вывод `operator<<` помечает перемещённый объект `(moved-from)`.

Итог демо: за перемещение — 0 аллокаций и 10 не переписанных значений, но
источник превращается в безопасную «пустышку»; за копирование — `new` буфера и
копирование данных, зато источник цел.
